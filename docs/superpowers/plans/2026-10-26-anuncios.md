# Plan de implementación — Anuncios (plan 2 de 5)

> **Para quien ejecute este plan:** SUB-SKILL OBLIGATORIA: usa `superpowers:subagent-driven-development` o `superpowers:executing-plans` para implementarlo tarea por tarea. Los pasos usan casillas (`- [ ]`).

**Objetivo:** que una madre pueda fotografiar un lote de ropa desde el móvil y publicarlo en menos de un minuto, y que cualquiera pueda abrir su ficha y verla.

**Arquitectura:** una sola tabla `anuncios` para prenda y lote, porque comparten fotos, situación, búsqueda y —en los planes siguientes— conversaciones y favoritos. Las fotos van a un almacén de Supabase y se procesan **en el navegador antes de subirlas**: redimensionar y borrar los metadatos son el mismo gesto, porque volver a dibujar la imagen en un lienzo descarta todo lo que no sean píxeles, incluidas las coordenadas GPS. Las reglas de quién puede publicar y editar qué siguen viviendo en PostgreSQL.

**Tecnologías:** las del plan 1, más el almacenamiento de Supabase. Sin librerías nuevas de imagen: el lienzo del navegador basta.

**Especificación:** `docs/superpowers/specs/2026-10-20-marketplace-ropa-infantil-hito1-design.md`
**Plan anterior:** `docs/superpowers/plans/2026-10-21-cimientos-y-cuentas.md`

## Restricciones globales

Las del plan 1 siguen vigentes. Añade estas:

- **El lote es ciudadano de primera, no una casilla.** Rango de tallas, número de piezas y **precio por pieza calculado y visible**. Es el argumento de venta del nicho y ningún generalista lo muestra.
- **Ninguna foto conserva sus metadatos.** Las fotos de móvil llevan las coordenadas de donde se tomaron; publicarlas sería publicar dónde vive una familia con niños pequeños.
- **Prohibidas las fotos con personas.** Aviso visible en el propio subidor, no escondido en las condiciones.
- **Publicar exige `puede_publicar()`**: correo verificado, no estar bloqueado y haber declarado una fecha de persona adulta. Lo comprueba PostgreSQL, no la pantalla.
- **Un anuncio vendido no se borra.** Su página sigue viva marcada como vendida, por lo que explica la sección 7 del diseño.
- **Precio en céntimos**, entero y mayor que cero.
- **Todo anuncio admite al menos una forma de entrega**: en mano, envío, o las dos.

## Foco de revisión

Cinco entradas que el diseño da por supuestas y que conviene pinchar a propósito. Cada una tiene su prueba asignada.

1. **Una foto con coordenadas GPS dentro.** Debe llegar al almacén sin ellas. Es el punto que más daño hace si falla. → Tarea 4.
2. **Un lote con rango invertido** (de 6 meses a 3 meses) o con cero piezas. → Tarea 1.
3. **Precio de 0 €, negativo, o de 99.999 €.** → Tareas 1 y 3.
4. **Alguien que edita el anuncio de otra persona**, llamando a la API directamente. → Tarea 1.
5. **Alguien sin fecha de nacimiento declarada** (ha entrado con Google) que intenta publicar. → Tarea 1.

```sql
-- Las categorias son tabla de referencia, como las tallas y las
-- provincias: su codigo va en las direcciones publicas del catalogo y si
-- fuera texto libre "pijama", "Pijamas" y "pijamitas" serian tres sitios
-- distintos. Su copia en TypeScript esta en src/lib/anuncios/modelo.ts y
-- la tarea incluye una prueba de paridad, como las que ya existen.
create table categorias (
  codigo text primary key,
  etiqueta text not null unique,
  orden int not null unique
);

alter table categorias enable row level security;
grant select on table categorias to anon, authenticated;
create policy "las categorias las lee cualquiera"
  on categorias for select to anon, authenticated using (true);

-- Las 17 filas salen de CATEGORIAS en src/lib/anuncios/modelo.ts.

create type tipo_anuncio as enum ('prenda', 'lote');
create type situacion_anuncio as enum ('activa','reservada','vendida','retirada');
create type estado_conservacion as enum
  ('nuevo-con-etiqueta','como-nuevo','buen-estado','con-senales-de-uso');
create type temporada as enum ('verano','invierno','entretiempo','todo-el-ano');
create type genero_prenda as enum ('nina','nino','unisex');
create type talla_real as enum ('pequena','normal','grande');

create table anuncios (
  id uuid primary key default gen_random_uuid(),
  -- Seis caracteres, no secuencial: va en la direccion publica y permite
  -- reescribir el texto del enlace sin romperlo.
  id_publico text not null unique
    default lower(substr(replace(gen_random_uuid()::text,'-',''), 1, 6)),
  slug text not null,
  vendedor uuid not null references perfiles(id) on delete cascade,
  publicado_por uuid references perfiles(id),

  tipo tipo_anuncio not null,
  titulo text not null,
  descripcion text,
  defectos text,

  talla text not null references tallas(codigo),
  talla_hasta text references tallas(codigo),
  numero_piezas int,
  desglose text,

  categoria text not null references categorias(codigo),
  genero genero_prenda,
  marca text,
  color text,
  estado estado_conservacion not null,
  ajuste talla_real not null default 'normal',
  temporada temporada,

  precio_centimos int not null,
  acepta_entrega_mano boolean not null default true,
  acepta_envio boolean not null default false,
  zona_encuentro text,

  provincia text references provincias(codigo),
  ciudad text,
  situacion situacion_anuncio not null default 'activa',
  publicado_el timestamptz not null default now(),
  vendido_el timestamptz,
  actualizado_el timestamptz not null default now(),

  constraint precio_positivo check (precio_centimos > 0),
  constraint precio_razonable check (precio_centimos <= 100000),
  constraint lote_con_piezas check (
    (tipo = 'prenda' and numero_piezas is null and talla_hasta is null)
    or (tipo = 'lote' and numero_piezas >= 2)
  ),
  constraint alguna_entrega check (acepta_entrega_mano or acepta_envio),
  constraint titulo_con_contenido check (length(btrim(titulo)) between 3 and 120)
);

-- El rango de tallas no puede ir hacia atras. Se compara por el orden de
-- la tabla de tallas, no por el texto: "12-18-meses" es mayor que
-- "3-6-meses" aunque alfabeticamente no lo parezca.
create or replace function rango_de_tallas_valido()
returns trigger language plpgsql set search_path = public as $$
declare
  desde int; hasta int;
begin
  if new.talla_hasta is null then return new; end if;
  select orden into desde from tallas where codigo = new.talla;
  select orden into hasta from tallas where codigo = new.talla_hasta;
  if hasta <= desde then
    raise exception 'El rango de tallas va hacia atras'
      using errcode = 'check_violation';
  end if;
  return new;
end;
$$;

create trigger anuncios_rango_valido
  before insert or update on anuncios
  for each row execute function rango_de_tallas_valido();

alter table anuncios enable row level security;

grant select on table anuncios to anon, authenticated;
grant insert on table anuncios to authenticated;
grant update (titulo, descripcion, defectos, precio_centimos, situacion,
              acepta_entrega_mano, acepta_envio, zona_encuentro, desglose)
  on table anuncios to authenticated;
grant delete on table anuncios to authenticated;

-- Los anuncios vivos los ve cualquiera, sin cuenta: el catalogo tiene que
-- ser visible para Google. Los retirados, solo su duena.
create policy "los anuncios vivos los ve cualquiera"
  on anuncios for select to anon, authenticated
  using (situacion <> 'retirada' or vendedor = auth.uid());

-- Publicar exige haber verificado el correo y declarado la edad.
create policy "publica quien puede publicar"
  on anuncios for insert to authenticated
  with check (vendedor = auth.uid() and puede_publicar());

create policy "cada quien edita sus anuncios"
  on anuncios for update to authenticated
  using (vendedor = auth.uid()) with check (vendedor = auth.uid());

create policy "cada quien borra sus anuncios"
  on anuncios for delete to authenticated using (vendedor = auth.uid());

create index anuncios_por_talla on anuncios (talla, situacion);
create index anuncios_por_provincia on anuncios (provincia, situacion);
create index anuncios_recientes on anuncios (publicado_el desc);
```

create table fotos (
  id uuid primary key default gen_random_uuid(),
  anuncio uuid not null references anuncios(id) on delete cascade,

  on fotos for select to anon, authenticated using (true);

create policy "cada quien sube fotos a sus anuncios"
  on fotos for insert to authenticated with check (
    exists (select 1 from anuncios a
             where a.id = anuncio and a.vendedor = auth.uid())
  );

create policy "cada quien borra las fotos de sus anuncios"
  on fotos for delete to authenticated using (
    exists (select 1 from anuncios a
             where a.id = anuncio and a.vendedor = auth.uid())

insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('anuncios', 'anuncios', true, 2097152,
        array['image/webp','image/jpeg'])
on conflict (id) do update set
  file_size_limit = excluded.file_size_limit,
  allowed_mime_types = excluded.allowed_mime_types;

-- El archivo tiene que vivir en la carpeta del anuncio de quien lo sube.
create policy "subir fotos a la carpeta de un anuncio propio"
  on storage.objects for insert to authenticated with check (
    bucket_id = 'anuncios'
    and exists (
      select 1 from anuncios a
       where a.vendedor = auth.uid()
         and (storage.foldername(name))[1] = a.id::text
    )
  );

### Tarea 4: Preparar las fotos en el navegador

La tarea del foco de revisión número 1, y la más delicada del plan.

**Archivos:**
- Crear: `src/lib/imagenes/preparar.ts`
- Prueba: `tests/unidad/preparar-imagen.test.ts`, `tests/e2e/fotos.spec.ts`

**Interfaces:**
- Produce: `prepararFoto(archivo: File): Promise<{ blob: Blob; ancho: number; alto: number }>`.

**La idea, que resuelve dos problemas con un solo gesto:** se dibuja la imagen en un lienzo y se vuelve a exportar. El lienzo solo conserva píxeles, así que la exportación sale **sin ningún metadato** —incluidas las coordenadas GPS— y de paso se redimensiona. No hace falta ninguna librería que "limpie EXIF": limpiar es un efecto de volver a dibujar.

Que una imagen de 4000 px se reduzca a 1600 en el lado largo, que una de 800 no se agrande, y que la proporción se conserve. Son funciones puras: `calcularTamano(ancho, alto)`.

## Estado al cerrar el plan — 29 de octubre de 2026

Las nueve tareas están hechas. 232 pruebas de unidad y de permisos, y 11
de recorrido completo, todas en verde contra la base de pruebas.

Lo que apareció por el camino y no estaba en el plan:

- **Los permisos por columna no restringían nada.** Supabase concede todo
  por omisión sobre cada tabla nueva del esquema público, y un
  `grant update (columna…)` solo añade. La lista cuidadosa de la tarea 1
  era decorativa: desde el navegador se podía falsear `vendido_el` —el
  número con el que se mide el proyecto—, `publicado_el`, la talla o el
  tipo de un anuncio propio. Lo cierra la migración 0010, con tres capas:
  quitar el permiso general, una segunda cerradura dentro de
  `sellar_venta`, y cambiar los permisos por omisión para que la próxima
  tabla nazca cerrada. Hay una prueba que lo vuelve a comprobar entero.
- **Deshacer una venta no borraba la fecha.** Marcar vendido por error
  pasa; dejar la fecha puesta estropearía el único número que importa.
- **No había ninguna barra de navegación.** A «Publicar» y a «Tus
  anuncios» solo se llegaba escribiendo la dirección a mano.
- **Un anuncio puede publicarse sin alias.** El alias no es obligatorio
  y nada lo exige para publicar, así que una ficha puede quedarse sin
  nombre con el que llamar a quien vende ni enlace a su armario. La ficha
  lo aguanta («Una familia de la plataforma»), pero en una plataforma
  donde dos desconocidas quedan en la puerta de un metro, la confianza es
  el producto.
  La salida evidente —exigir alias en `puede_publicar()`— es peor: manda
  a quien acaba de registrarse a inventarse un apodo antes de dejarle
  subir la primera foto, que es justo el tropiezo que vacía un catálogo
  recién nacido. Así que la migración **0011** hace que cada perfil nazca
  con uno puesto, `familia-a1b2c3`, cambiable en el perfil. No se saca
  del correo a propósito: el alias va en una dirección pública y la parte
  de delante de un correo suele llevar nombre y apellido.
  Aplicada y comprobada en pruebas, con siete pruebas en
  `tests/permisos/alias.test.ts`: que un perfil recién creado ya lo trae,
  que vale como dirección pública, que no sale del correo, que no se
  repite, que no se puede dejar en blanco, y que un anuncio recién
  publicado ya sabe decir quién lo vende. Falta llevarla a producción con
  las otras tres.

Lo que sigue sin existir, a propósito: el catálogo y la búsqueda (plan 3),
los mensajes entre quien compra y quien vende (plan 4). La ficha lo dice
con todas las letras en vez de enseñar un botón que no lleva a ninguna
parte.
